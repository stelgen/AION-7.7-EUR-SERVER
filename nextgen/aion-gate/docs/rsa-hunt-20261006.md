## ЧТО РАБОТАЕТ (доказано живым клиентом)
- Blowfish = **little-endian** блоки (BigEndian был корневым багом, исправлен)
- Welcome = **opcode-first**: [0]=0x00 SM_INIT, [1:5]=sid (СЧЁТЧИК с 1, не rand!), [5:9]=V (=authd [03]-payload, у нас 0x0000c621=50721; у ориг 3), [9:137]=модуль, [137:153]=GG(нули ок), [153:169]=key2, [169:173]=65 65 00 72; +4 нуля → 177 → csum@184 → ECB(key1) → 194
- key2 = LUT[r],LUT[r&0xc1],LUT[r&0xf2],LUT[r&0x23] ✓ (крэк: нулевой ECB-блок 179214a5dae3c577 + перебор r)
- Клиент ПРИНИМАЕТ наш welcome и шлёт AUTH_GG = [07][sid=НАШ][27×0][12Б хвост "PRO\x07?ROL_VE"-вариативный]
- Наш echo 42b = EncryptSecondary([0b][sid][27×0]+dup) — клиент принимает
- Клиент шлёт LOGIN 312/314b → **НАША RSA-расшифровка отрабатывает (declen=128), НО decbuf = МУСОР** (не [login][md5])
- Relay [02] в authd уходит, **authd МОЛЧИТ на мусорный decbuf** → клиент «думает»
- 26b-эмуляция: op=0x05 → 42b server-info [04][01 01 01][worldIP][611e=7777][0000][f4010101][00000002][010001][12x0]; op=0x02 → 26b [07][01][1010][01][6x0] — СТРУКТУРА с capture, но живой клиент-тест НЕ ПОДТВЕРЖДЁН (клиент не доходил)
- authd ответы: 74b/42b/26b/18b = EncryptSecondary(payload от authd) 64/32/16/8Б — relay по id реализован
- **18b = LoginFail** (authd payload 8Б; пойман при не-ASCII логине)
- **authd ПАРОЛЬ НЕ ПРОВЕРЯЕТ**: login=1 + pass 1/2/3/11/русская-a = один акк (авто-создание); login=stelgen+pass=1 = акк StelGeN; фейл ТОЛЬКО не-ASCII логин → 18b

## ЕДИНСТВЕННЫЙ БЛОКЕР: RSA-decbuf мусор
decbuf = ct^d17 mod N_наш = 128Б случайщины. Гипотезы:
1. **Клиентский plaintext ≠ [login16][md5-16]** — перебор 6144 гипотез (24 перестановки скрамбла × cum-варианты × оффсеты 5-12 × BE/LE × m-формы ascii/utf16/md5-обе/raw32 × e 17/65537) с правильным ct=128Б — ПУСТО. ЛИБО PKCS#1-пэддинг с рандомом (тогда m случайно каждый раз — оракул слеп), ЛИБО другая раскладка
2. **Клиентский unscramble ≠ классика** — наш «фикс» (реверс порядка = инверс классики) мат-верен, но живым RSA НЕ подтверждён. Если клиент анскрамбит ИНАЧЕ → N_client ≠ N_our → decbuf мусор ✓ сходится
3. e клиента ≠ 17 — перебор E ∈ {3..65537} на N_our по структурному признаку (m[0]==0x31) — ПУСТО (но критерий требует знание раскладки!)

## УМЕРШИЕ ТЕОРИИ (НЕ ВОЗВРАЩАТЬСЯ)
- Pub.key-файл как RSA-источник: замена Pub.key (наш DER и нули) → «????(x64)[1024] не удалось подключиться» ПРИ КОННЕКТЕ; N_pub (EF1A2640...) ОТСУТСТВУЕТ в памяти AuthGateD (head8/tail8/rev — 0 попаданий); m^e mod N_pub == ct — не совпало ни одной раскладкой/е
- СКАМРАМБЛ-ФИКС «инверс классики» решает RSA — НЕТ (live-тест 1/1 дал мусорный decbuf)
- m = [login][md5] раскладка — НЕ подтверждена ни разу ни одной сессией
- «наш decbuf мусор из-за wrong-e 17» — перебор E пуст (но зависел от m-раскладки!)
