# 📡 R1 aion-npc — capture 2002: блокер loopback + собранный golden-материал (08.10)

## 1. Попытка capture (факт)

- `pktmon filter add NPC2 -p 2002; pktmon start --capture --pkt-size 0 --comp nics` → **0 пакетов**: pktmon `comp list` = ТОЛЬКО `Red Hat VirtIO Ethernet Adapter` — loopback-компонентов НЕТ, 127.0.0.1-трафик не захватывается. tshark/Wireshark/Npcap на VM нет. `timeout /t` в cmd без консоли падает (input redirection) — юзать `ping -n N 127.0.0.1 >nul`.
- **Вывод**: пассивный сниф loopback 2002/2006/2007/2009 на этой VM невозможен штатными средствами. Леджер: думали «pktmon пассивно всё видел (опыт 7777)» → 7777 шёл по LAN-NIC от клиента, внутренние каналы — 127.0.0.1 → мимо NIC.
- ⚠️ **Кросс-пульс aion-cache**: их R1-план «pktmon 2006» упрётся в тот же блокер; спасение у них уже есть — `log/*.log` 356МБ (RPC-строки). Стек-вывод: ВСЕ внутренние каналы (2002/2006/2007/2009/2051) loopback — wire их ловим только (а) собственным листенером (fork-стенд/тень), (б) тест-миром на LAN, (в) штатными логами NC.

## 2. Собранный golden-материал БЕЗ capture (live)

**a) Мир-цикл NPCSvr64 из `.err` (aionlog npc, live 08.10 11:29–11:33):**
- `World::MoveNPC(<180.4 млн times called>) :: World(LF4, 210050000)`, `World(DF3, 220040002)`, `takes (31)>20ms at (x,y,z)`, `(User:0, Npc:26..83)` — MoveNPC спамится непрерывно (мир жив, юзера нет); миры поимённо: LF4=210050000, DF3=220040002; счётчик User/Npc на мир.
- Таймер-движок: `WaitThread(), Too many timer pops in a loop, passedTick: 0/15/16 (include lock waiting), PopedTimerCount: 11000–21000` каждые ~5с — **периодика тиков ~5с, 11–21К таймеров за тик** (масштаб мир-цикла для R3-планировщика; «Too many timer pops» = штатная диагностика перегруза тика).
- `LogClientSocket::AlivePacket` ×2 каждые ~90с — 2051-канал жив (массив в парах = два лог-сервера/канала).

**б) Wire-каркас 2002 из PDB Server64 (148 хендлеров с семантикой):** `docs/npcsvr-2002-handlers-raw.txt` — ServerToNPCServer ×86 (Send*/Encode*), NPCServerToServer ×62 (Decode*); типы аргументов в мангл-сигнатурах = порядок сериализации (PointFloat, KillerInfo, QuestShareInfoMultiple, EmotionType, NameIdType). Метод = как у cache («dispatch восстанавливается без дизasmа»).

**в) Хендлы бинаря для будущего wire-лога**: `FileLog::AddPacketLog`, `PacketProfileLogger` (NPCSvr64) — штатная packet-лог-машина есть; ищем конфиг-флаг активации (применится при рестарте пары — только по «го»).
