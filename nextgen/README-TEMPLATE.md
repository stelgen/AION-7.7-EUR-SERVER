# 🧩 README-TEMPLATE — стандарт README для подпроектов nextgen

> Каждый nextgen-проект (и будущие тоже) ведёт README строго по этой структуре.
> Правило юзера: «README должны быть понятны агенту и выглядеть как взрослые серьёзные гиты».
> Взгляд на страницу = агент сразу знает статус, канон, где артефакты и сурсы, как деплоить/откатывать и что делать дальше — и ОБЯЗАН продолжать обновлять документ.

---

```markdown
# <имя> — <что заменяет/делает> (<язык>)

> **ЕДИНАЯ СТАТУС-ШАПКА (обязательный формат, первой строкой под заголовком):**
> `<символ> <статус> · ~<NN>% · <дата>` — например: `✅ РЕЛИЗ · 100% · 08.10` / `🟡 каркас · ~45% · 07.10` / `⬜ деприор · 0% · —`.
> Далее: релиз/коммит, exe-sha, где живёт на проде (или «НЕ деплоен»), следующий шаг одной строкой.
> Легенда символов — [WORKFLOW.md §1.1](WORKFLOW.md): ✅ в бою/релиз · 🟡 каркас/в работе · 🔬 ресёрч · ⬜ не начат/деприор · ⏳ ждёт «го».

## 📊 Статус и фазы
- Таблица фаз (R0..R6) с датами и ✅/⏳/⬜ + общий % (по фазам, честно — см. WORKFLOW §1.1: не «почти готово», R2 из 7 фаз ≈ 30–45%).
- Что работает сейчас / что НЕ работает (блокеры отдельной строкой).

## 📟 Канон протокола (только проверенные факты, «НЕ трогать»)
- Wire-формат, опкоды/команды, крипта, state-машина — таблицами.
- Каждая строка = проверено (capture/дизasm/сорс эталона/live), не догадки.

## 🧱 Структура / сборка
- Дерево кода; `go vet ./... && go test ./...`; команды сборки linux+windows; конфиг-пример (без секретов).

## 🧪 Тесты и верификация
- Что golden, что e2e, чем проверялся ориг (probe/forkprobe/fake-клиенты).

## 📦 Артефакты — где лежат
| Что | Гит | VM | Локально |
|---|---|---|---|
| код/конфиги | ... | D:\SAION\<svc>\ ... | ... |
| capture/fixtures | ... | C:\Temp\... | ~/STELGEN/tmp/... |

## 🗂 Сурсы-эталоны (приоритет над дизасмом)
- Таблица: сурс → где → что из него берём (сорсы-эталоны > PDB publics > дизasm > догадки).

## 🚢 Деплой и откат
- Деплой по шагам (задача AionXxx, run.cmd, D:\SAION\<svc>\); ОТКАТ одной командой (проверенный).

## 📜 Логи
- Что пишем, куда, raw-first (см. LOGGING-SPEC), ship-события, баннер-канарейка.

## 🧪 Журнал теорий / леджер решений (в ROADMAP-файле компонента)
- Каждая гипотеза фиксируется с датой + способ проверки (⏳); после проверки — ✅ канон (в README) или ❌ удалена из канона СРАЗУ, остаётся строка в леджере (что думали → почему нет → чем доказали).

## 🚧 Блокеры / открытые вопросы
- Нумерованный список с ссылкой на фазу.

## ⏭️ Следующий шаг (для нового чата)
- Конкретный пункт + ссылка на PROMPT (в папке компонента) / ROADMAP + `WORKFLOW: <имя>` ([WORKFLOW.md](WORKFLOW.md)).
```

---

## Правила ведения

1. **Статус-строка сверху** всегда свежая (дата, коммит, exe-sha, где живёт).
2. **Канон-факты = только проверенные.** Догадки/гипотезы — в блокеры или в «историю решений», не в канон. Старое неправильное — удалять/помечать, не тащить.
3. **Артефакты-таблица** обязательна: где код, где capture, где PDB, где эталоны — агент не должен искать.
4. **Откат** описывается как одна команда, проверенная на практике.
5. **PROMPT.md** (в папке компонента) = готовый копипаст для нового чата (контекст + канон + готчи + план); закрытые помечаются `> ⚠ АРХИВ — задача закрыта, док сохранён для истории`.
6. **Новые компоненты — self-contained**: в папке лежат README.md + ROADMAP.md (с журналом теорий) + PROMPT.md + (для кодовых) config.example.yaml; внешние `nextgen/PROMPT-*.md`/`*-ROADMAP.md` — наследие ранних треков, новые файлы так не кладутся.
7. Дополняй README в том же чате, где пишешь код, — не «потом».
8. Процесс запуска/пульса/чистки лжи: [WORKFLOW.md](WORKFLOW.md) — юзер пишет `WORKFLOW: <имя>` и агент сам всё находит и продолжает.
9. **Статус-сдвиг = 3 места + память, один коммит**: шапка этого README → строка/д/% в стек-таблице [README.md §2](README.md) и дашборде §2.5 → сводка root [../README.md](../README.md) → дельта в страницу памяти. Нарушение симметрии = потерянный статус при смерти чата.
