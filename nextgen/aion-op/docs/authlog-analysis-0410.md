# Анализ AuthD\etc\log + Server64: почему «Ни один игровой сервер не закреплён за сервером авторизации» (04.10.2026)

READ-ONLY анализ. Локальная копия логов: `STELGEN/tmp/aion-vm/authlogs/` (весь `AuthD\etc\log` + `MainServer\log\2020-06-04.err`).

## TL;DR — РУТ-КОЗ

**Authd отдаёт клиенту в server list адрес мира из таблицы `AionAccounts..server`, и этот адрес СМЕНИЛСЯ между 03.10 и 04.10:**

```
03.10 (весь день, ВСЕ входы работали):  Auth->Gate(4): c0a8007d:611e = 192.168.0.125:7777
04.10 (весь день, ВСЕ входы падают):    Auth->Gate(4): 51193bc2:611e = 81.25.59.194:7777
```

Клиент логинится на 2106 нормально (прокси), получает server list с `81.25.59.194:7777`, жмёт коннект — TCP до игрового порта НЕ доходит (снаружи/через VPN), мир ждёт 30 сек (`aboutToPlayTimer=30000`) и клиент отваливается с ошибкой «Ни один игровой сервер не закреплён за сервером авторизации». Сессия на auth-уровле живёт 32–35 с и закрывается. **Auth НЕ сломан** — вся аутентификация проходит (AgeCheck/FindAccount/InitLoginUserData OK в каждой попытке); сломан последний шаг: адрес мира, по которому клиент должен открыть игровое соединение.

## Доказательная цепочка

### 1. `Auth->Gate(4)` — адрес в server list (packet-логи authd)
- 03.10 08:36 … 23:05 (все логины дня): `0100/0101 01 c0a8007d 611e …` → **192.168.0.125:7777**
- 04.10 00:36 … 06:59 (все логины дня): `0101 01 51193bc2 611e …` → **81.25.59.194:7777**
- Смена подхватилась на **регистрации мира 04.10 00:31** (новый World->Auth сокет 628): authd кэширует адрес мира на момент регистрации Server64, правки таблицы `server` без перерегистрации мира не применяются (03.10 22:46 ещё отдавался старый IP после дневных правок БД).

### 2. `dual`/`use` логи — длительность сессий
- 03.10: десятки коротких сессий при тестах + **успешные длинные: 10:35:32→12:01:54 = 5182 с (86 мин в мире), 22:46:01→22:55:40 = 579 с (~10 мин в мире)**
- 04.10: **НИ ОДНОЙ сессии длиннее 46 с** — все 32–35 с = «логин → выбор сервера → 30 с ожидания → обрыв» (ровно aboutToPlayTimer=30000).

### 3. Server64 `2020-06-04.err` (MainServer\log) — мир ЖДАЛ клиента
- В последнем ране (старт ~06:08 04.10) — ровно **5 записей** `AboutToPlayerTimer ::== Client(Acct: 1010) is not connected` = 5 попыток 06:33/06:46/06:53/06:55/06:59: Server64 **принял** вход, отправил AboutToPlay, но клиент за 30 с не установил TCP 7777.
- В ране от 03.10 12:12 — 3 таких записи (12:19/12:21/12:23) — тогда мир ещё спавнился после рестарта (NPCSvr до 12:39), та же сигнатура «принял — клиент не пришёл».

### 4. ОПРОВЕРЖЕНИЕ «теории счётчика» (в памяти была НЕВЕРНАЯ инфа)
Ранее считали: `World->Auth f2030000+NN`, где NN=01 принять, 02+ = отказ/утечка счётчика. **Логи это опровергают:**
- 03.10 10:35:36 `f2030000**02**` → юзер вошёл в мир и играл 86 минут (heartbeat'ы чара `ea030000`=1002 в World->Auth 10:41–12:01).
- 03.10 22:46:05 `f2030000**05**` → юзер вошёл в мир, играл ~10 мин (heartbeat `f203000001ea03000009000000…` 22:46:27).
- NN = просто порядковый номер попытки/сессии с момента старта Server64. Код отказа в NN НЕТ.
- `f2030000cb000000…` от мира в authd — это **нотификация LOGOUT** (время бит-в-бит совпадает с LOGOUT в dual-логе: 08:37:31, 12:01:54, 06:33:56…), а не отказ.
- «Рестарт пары перед игрой» был плацебо: 04.10 пара рестартовалась 9+ раз (03:10, 03:37, 03:57, 05:12, 05:29, 05:50, 05:54, 06:27, 06:52 — все видны как новые World->Auth сокеты), входов всё равно не было, потому что IP в server list оставался недостижимым.

### 5. Хронология попыток (dual, 04.10) — все 32–35 с
00:36, 00:39, 00:40, 01:57, 02:00, 02:08, 02:09, 02:17, 02:28, 02:38, 02:40, 02:55, 02:58, (03:02 test), 03:18, 03:44, 03:48, 04:04, 04:20, 04:22, 04:35, 05:18, 05:35, 06:33, 06:46, 06:53, 06:55, 06:59 — **ни одного входа в мир**.

## Почему 81.25.59.194 недостижим, а 192.168.0.125 был достижим
Клиент ходит через VPN (источник для VM — 89.47.164.187, VPN-выход). Через VPN-туннель доступен **LAN** (192.168.0.125 — проверено 03.10, весь день). Внешний WAN 81.25.59.194:7777 требует проброса порта на роутере — для 2106 он есть (логин проходит!), для 7777 — нет/не работает с этого vantage. Hairpin из домашней LAN не в счёт — клиент не в LAN.

## План решения (НА ВЫБОР, ничего не применено)

**Вариант A (рекомендую, проверен фактом 03.10):**
1. `UPDATE server SET ip='192.168.0.125' WHERE name='_MAIN'` (AionAccounts; inner_ip=127.0.0.1 НЕ трогать!).
2. Рестарт пары Server64+NPCSvr → мир перерегистрируется → authd начнёт отдавать 192.168.0.125:7777.
3. Проверка клиентом: логин → выбор сервера → вход (должно работать как 03.10).

**Вариант B (внешний IP для игры без VPN):** пробросить 7777/tcp на роутере → 192.168.0.125 (или поднять второй прокси 7777 по образцу aionproxy.py) и оставить ip=81.25.59.194. Минус: клиент с IP-проверкой может ругаться на неофициальный адрес — тогда + `version.dll`-патч (уже в гите tools/AionVersionDll_bin_1.6.2.zip).

**Быстрая проверка гипотезы с клиента (1 мин):** `Test-NetConnection 81.25.59.194 -Port 7777` и `Test-NetConnection 192.168.0.125 -Port 7777` с компа юзера — первый должен падать, второй проходить.

## Где смотреть логи (карта)
- `D:\AION_LIVE_SERVER\AuthD\etc\log\YYYY-MM-DD.HH.packet` — hex-пакеты; `.winlog` — ClientLoginTry/ServerDown; `.dual` — LOGIN/LOGOUT сессий; `.use` — длительности; `.err` — ошибки authd.
- Смена адреса мира в server list = строки `Auth->Gate(N),4,<hex>` в .packet (байты 4-7 = IP LE, 8-9 = порт LE).
- Server64: `D:\AION_LIVE_SERVER\MainServer\log\2020-06-04.err` (имя = RunAsDate-дата, время внутри заморожено на «16:28» — сопоставлять по позициям/событиям, не по таймстампам).
